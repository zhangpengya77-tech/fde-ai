## A. 五種學員篩選

| # | 選項 | 參數值 `s_state` | 判定依據（既有資料，不代表考核合格） |
|---|------|------------------|--------------------------------------|
| 1 | 全部學員（預設） | `""` | 不過濾 |
| 2 | 尚未提交任何 R01–R08 | `none` | 已提交成長紀錄數 = 0 |
| 3 | 部分提交（1–7 項） | `partial` | 1 ≤ 已提交數 ≤ 7 |
| 4 | 八項已提交（8 項） | `complete` | 已提交數 = 8 |
| 5 | 有待複核成果 | `pending` | 至少一筆真實待複核紀錄（submitted 且未 reviewed） |

- 「已提交」沿用 P3 既有語意 `GROWTH_SUBMITTED_STATUSES = {SUBMITTED, NEEDS_REVISION, APPROVED, REJECTED}`；`pending` 另計入任務提交（type=task 且 status=submitted）。
- **明確標示語意**：選項文字為「八項已提交」，非「已完成／已通過」；教師端不因此判定合格。
- 非法值安全回落至 `""`（全部學員），不報錯。
- 篩選無結果時顯示「沒有符合篩選條件的學員。」（與「此班級目前尚無在學學員。」區分）。

實作位置：`student_portal/learning/views.py` 常數 `PROGRESS_FILTER_OPTIONS`（五項）＋ `_progress_filter_matches(row, progress_filter)`；模板以 `progress_filter_options` 迴圈產生。

### B.4 五種學員篩選逐班驗證（頁面學員集合 vs DB 期望，全部一致）

| 班級 | 全部 | none | partial | complete | pending |
|------|------|------|---------|----------|---------|

| B 班 | 3（B1,B2,B3） | 1（B1） | 1（B2） | 1（B3） | 0 |

- **B 班 `pending = 0` 之成因（重要語意差異，如實揭露）**：頁面與 DB 期望皆為 0，兩者一致，但與卡片數字（待複核成果 = 1）看似矛盾，原因為**兩者統計母體不同**：
  - 卡片「待複核成果」＝ `pending_total`，母體為 **待複核清單項目**（成長紀錄 `submitted` ＋ 所有 `submitted` 任務）→ B 班 = 0（成長）＋ 1（B2 的 T06 任務）= **1**。
  - 進度篩選 `pending` ＝ `row["pending_count"] > 0`，而 `pending_count` 母體僅為**成長紀錄且狀態恰為 `SUBMITTED`**（不含任務、不含 `needs_revision`）→ B 班 = **0**。
  - 因此 B 班 `pending` 篩選為 0 位學員，與卡片 1 筆並存並非缺陷，而是既有 P4/P4.1 定義：**卡片計入任務提交，進度篩選不計入**。本輪未變更此定義，已列入 §G.3 風險與 §十 待確認第 1 項，供教師決定是否統一。

### D.1 四種排序（逐筆順序驗證，A/B 兩班）

| 排序 | 主鍵 | 穩定次要鍵 |
|------|------|-----------|
| `oldest`（預設） | submitted_at 升序 | 學員名稱 → 紀錄編號 |
| `newest` | submitted_at 降序 | 學員名稱 → 紀錄編號 |
| `student_asc` | 學員名稱（**Unicode 字元排序**） | 紀錄編號 → 提交時間 |
| `record_asc` | 紀錄編號（R 群先於 M 群、群內數字升序） | 學員名稱 → 提交時間 |

- **提交時間缺失者（A2 的 R04）在 `oldest` / `newest` 下一律排最後**（以 aware 下限值 `PENDING_TIME_FLOOR` 作鍵，避免 naive/aware 比較錯誤）。
- 任意兩列皆有全序：相同名稱、相同時間不會造成順序不固定（單元測試以兩次請求結果一致固定）。
