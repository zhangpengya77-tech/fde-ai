## E. 根因判定

### E.1 結論（確認程度：**HIGH / 已確認**）

**8770 上同時存在兩個常駐 python 程序（16500、26380）在同一個 IPv4 tuple `127.0.0.1:8770` 上 LISTEN（Windows socket 共用 / SO_REUSEADDR 造成的重複監聽）。**
先前觀測到的「PID 在 16500／26380 之間交替」**不是服務重啟**，而是**監測取樣假象**：`Get-V15CListenerPid` 以 `Get-NetTCPConnection -State Listen -LocalPort 8770 | Select-Object -First 1` 取值，而 `Get-NetTCPConnection` 對同一 tuple 的兩條重複監聽只回傳其中一條且不穩定；`netstat` 則穩定顯示兩條。

### E.2 機制（已由程式碼佐證）

- RAG 服務 `rag_http_server.py`（`RagRoot = C:\Users\admin\Documents\Codex\2026-08-30\new-chat\FDE-AI\rag\f450_v1\runtime`）使用 `ThreadingHTTPServer((args.host, args.port), RagHandler)`，預設 `127.0.0.1:8770`。
- `ThreadingHTTPServer` 繼承 `HTTPServer`，其 `allow_reuse_address = 1` → 設定 **SO_REUSEADDR**。
- **Windows 的 SO_REUSEADDR 語義**與 Linux 不同：允許第二個 socket **成功 bind 同一 address:port**（而非報 `address in use`）。因此第二個 RAG 實例啟動時不會失敗，直接與第一個**並存監聽**。

### E.3 假設逐一排除

| 假設 | 判定 | 證據 |
|---|---|---|
| 真正的服務重啟 | **排除** | 兩個 PID 的 CreationDate 固定（2026-10-27 18:39:55 / 22:53:28），全程無新 PID 出現，兩者皆存活；若為重啟，PID 與 CreationDate 會不斷更新 |
| 兩個常駐程序**交替**監聽 | **修正為「同時」監聽** | `netstat` 每 tick 同時顯示兩條 LISTENING；非交替，而是並存 |
| IPv4／IPv6 或不同位址造成觀測差異 | **排除** | `netstat -p tcpv6` 對 :8770 無任何行；兩條 LISTENING 行皆為 IPv4 `127.0.0.1` |
| 監督程序／排程干預 | **排除** | 無 RAG 專屬排程/服務；兩 PID 的父進程（14508、26384）皆已消失 |
| 監測腳本自身取樣錯誤 | **部分成立（放大器）** | `Get-V15CListenerPid` 的 `Get-NetTCPConnection … -First 1` 對重複 tuple 不穩定；此為「交替假象」的直接原因，但底層確實存在真實的重複監聽 |
