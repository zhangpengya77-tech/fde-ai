## 1. 流程

```text
學員讀取參數 → 對白名單參數按「申請修改」→ 輸入新值、勾選「已拆槳、已斷電池」→ 送出
   ↓（伺服器驗證白名單、範圍、幅度；同一參數同時只能有一筆未完成申請）
教師在自己負責的班級清單裡看到申請 → 批准或退回
   ↓（批准後 10 分鐘內有效，只能使用一次）
學員按「寫入飛控…」→ 寫入前檢查清單 → 再次勾選安全聲明 → 瀏覽器確認視窗顯示原值與新值
   ↓（全部通過才送出 1 次 PARAM_SET）
等待飛控回覆 → 讀回比對 → 結果回報伺服器（伺服器再比對一次讀回值）→ 紀錄為「已寫入並讀回確認」或「寫入失敗」
```

## 3. 六道寫入檢查

| # | 檢查 | 在哪裡檢查 |
|---|---|---|
| 1 | 飛控已上鎖（Disarmed），而且心跳正常 | 瀏覽器（writer.js），送出前即時判斷 |
| 2 | USB 連線正常 | 瀏覽器 |
| 3 | 參數在白名單內、在範圍內、幅度不超過 30% | 伺服器（建立申請時）＋瀏覽器（寫入前再查一次） |
| 4 | 「已拆槳、已斷電池」聲明：申請時勾一次、寫入前再勾一次 | 伺服器記錄＋瀏覽器 |
| 5 | 教師已批准、10 分鐘內有效、同一台飛控（System ID 相同）、飛控目前值仍等於申請時的原值 | 伺服器（狀態與時效）＋瀏覽器 |
| 6 | 確認視窗顯示原值與新值，使用者按確定 | 瀏覽器 |

**PARAM_SET 只能由寫入模組產生**：編碼器只接受帶著寫入能力物件的呼叫，這個物件只有 `writer.js` 使用，而 `writer.js` 會先跑完六道檢查。其他程式碼要送 `PARAM_SET`，在編碼這一步就會被拒絕。

**寫入後**：等待飛控回覆 3 秒；沒有回覆就依名稱補讀一次；仍沒有回覆則判定失敗。**不會自動重送 PARAM_SET**。

## 7. 人工驗收（教師執行，必須拆槳）

1. **拆下所有螺旋槳、斷開動力電池**，只用 USB 供電。
2. 學員帳號：連線 → 讀取參數 → 對 `ATC_RAT_RLL_P` 按「申請修改」→ 改成目前值的 +10% → 勾選聲明 → 送出。
3. 教師帳號：批准。
4. 學員帳號：寫入飛控 → 確認清單全部打勾 → 再次勾選聲明 → 確定。
5. 確認畫面顯示「寫入成功，讀回值一致」，申請紀錄變成「已寫入並讀回確認」。
6. **用 Mission Planner 交叉確認**：關閉網頁連線後，用 Mission Planner 讀取 `ATC_RAT_RLL_P`，數值要和網頁一致。
7. 把數值改回原值（再走一次申請流程），確認可以還原。
8. 用遙控器解鎖（**仍然拆槳**）後再試一次寫入：確認清單第一項顯示 ✘，寫入按鈕無法按下。
9. 記錄每一步的結果和截圖，狀態改為 PASS 或 FAIL。

## 8. 風險與回退

| 項目 | 說明 |
|---|---|
| 白名單上下限 | 尚未經教師確認（`PENDING_TEACHER_CONFIRMATION`） |
| 寫入在學員瀏覽器執行 | 伺服器無法強制瀏覽器端的檢查；伺服器負責批准、時效、單次使用與結果紀錄。所以前端的六道檢查和編碼器的寫入能力限制都有單元測試保護 |
| 回退 | 關閉 `FDE_GCS_ENABLED` 立即停用；要完全回退 P3，revert 本次 commit 並移除 `gcs_portal` 的 migration（只有這一張新表，不影響 learning 資料） |
